## 어떤 문제를 어떻게 고쳤나

1. **태그 제안 실패:** 기존에는 503으로 멈췄다. 이제 원문에 명시된 태그로 추가 호출 없이 복구한다. 동행·활동 등 단일 선택 그룹에서 여러 후보가 있으면 임의로 하나를 고르지 않는다. 실제 112건 중 19건에서 이 복구가 사용됐다.
2. **“음식점이나 카페”:** 명시한 OR 대안이 누락되면 문장 전체가 제한된 단순 문법과 일치하는 경우 두 종류를 보존해 복구한다. 모호한 조건이 붙으면 임의로 복구하지 않는다.
3. **“공원 바로 옆 카페”:** `바로 옆`을 위치 관계로 인식하지 못해 공원을 별도 방문 대상으로 강제하던 검증 코드를 수정했다. 실제 인접 거리를 확인했다고 표시하지 않는다.
4. **“카페 두 곳을 차례로”:** 원문에 카페가 한 번만 나와도, 명시된 두/세 곳의 순차 방문 수량과 같은 장소 종류가 일치하면 근거 구절을 재사용할 수 있게 했다. 단순히 추천 두 개를 원하는 경우와 구분한다.
5. **AI 형식·의미 검증 실패:** 필수 조건을 조용히 삭제하는 대신 조건 확인을 안내하도록 처리했다. 문법·라벨 길이·필수 배열 규칙도 프롬프트에 보강했다. 통신 장애는 별도 서비스 오류로 유지한다.
6. **실호출로 추가 확인한 오류:** “줄 안 서고”를 식당 종류 제외로 잘못 넣고, 제외 항목에 계약에 없는 `reason`을 추가한 응답이 있었다. 기념일 야장에서는 불필요하게 긴 기념일 모호성 설명을 생성하기도 했다. 대기 상태 부정과 장소 종류 제외를 구분하는 규칙 및 정확한 JSON 예시를 추가했다. 수정 후 대기는 `unsupported`, 야장은 `outdoor_seating=true, required=true`로 유지되고 두 해석 모두 통과했다.

## 남은 문제와 해석 시 주의

- 실제 112건의 안내 86건 중 **9건은 AI 해석 검증 미통과**였다(스키마 7, 종류 없음 1, 라벨 1). 모두 정상 추천이라고 계산하면 안 된다. 그 뒤 두 대표 문장의 프롬프트를 보강해 2건을 재확인했으며, 최종 프롬프트로 112건 전체를 다시 돌리지는 않았다.
- `QA-6407`(아산 배방역, “밥 먹고 산책한 다음 카페”)은 AI 순위 선택이 실패해 검증된 규칙 기반 코스로 대체됐다. 장소 데이터·코스 구조 검사 문제는 없었지만 AI 선택 성공으로 계산하지 않았다.
- 야외 좌석·실시간 대기·영업·가격 정보가 없는 것은 그대로다. 안내나 미확인 조건을 실제 충족 보장으로 바꾸지 않았다.
- 전체 DB의 초기 병렬 검사에서 추천 503이 나왔다. 오류 본문이 없어 모두 시간 초과라고 단정할 수 없다. 별도 전체 DB 단일 코스 확인은 약 9.95초로 성공했다. 동시 사용자 성능은 여전히 별도 확인이 필요하다.
- 휴대폰 UI·지도 SDK 검사는 이번 작업에 포함하지 않았다. 수정은 작업 폴더의 서버 코드에 반영했다.
