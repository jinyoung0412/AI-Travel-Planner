# QA·수정·전체 리뷰 진행 기준

2026-10-20 사용자 승인: 기획 채팅이 오케스트레이터로서 QA 결과를 확인하고, 발견된 문제를 기본 GPT-6.1 Sol High 하위채팅에 배정하여 수정·재검증한다. 이후 전체 코드 리뷰와 실제 정보 대조를 수행하고 추가 결함도 하위채팅에서 수정한다. 새 작업 채팅 생성·후속 지시·결과 확인은 이 범위에서 승인되었다. 원격 push·main 병합·배포는 별도 요청 없이 하지 않는다.

## 순서와 통과 기준

1. **실기기 QA 수신:** `01a1594b-9632-7a30-87f6-4225a2e1be43`, 최초 턴 `01a1594b-988d-7e41-a9bc-734924a31ee4`, host `local`. 기기는 이 채팅이 단독 소유하여 조작한다. 이 단계 동안 팀원 안내 작성 등 비간섭 작업만 진행한다.
2. **결함 분류와 수정:** 결과 파일·스크린샷·로그를 읽고 가능한 결함을 독립 재현한다. P0/P1을 우선으로 관련 기능별 수정 채팅을 만든다. 사용자 데이터 손실 가능성이 있는 P2도 우선 검토한다. 보고된 모든 항목에 해결/수정 불필요 근거/보류 사유를 붙인다.
3. **재검증:** 변경 파일과 회귀 테스트를 독립 검토하고 해당 실기기 경로도 다시 실행한다. 기기 조작자는 항상 한 명. 다른 채팅의 실험이 진행 중인 서버를 재시작하거나 소스/APK를 변경하지 않는다.
4. **전체 코드 리뷰:** 재현된 주요 QA 결함이 해소되고 남은 한계가 명시되면 시작한다. “문제가 전혀 없음”을 증명했다고 하지 않는다. 현재 실행 코드의 모든 자사 소스·플랫폼 설정·배포 설정·스크립트·문서를 목록화하고 파일별 검토 담당/상태를 기록한다. 생성 파일·외부 패키지는 제외 이유를 남기고 의존성 설정은 검토한다. 로컬/원격 추적 브랜치와 기준 차이는 읽기 전용으로 정리하여 누락 변경·중복 구현·오래된 사용법을 확인한다. 과거 브랜치를 임의로 병합하지 않는다.
5. **전체 리뷰 결함 수정:** 아래 영역별 High 채팅으로 분리하고 파일 소유권을 지정한다. 공유 계약 파일은 통합 담당만 수정하거나 순서를 조정한다. 수정 후 원래 재현 + 회귀 + 관련 실기기 경로를 통과해야 닫는다.
6. **최종 통합:** 전체 Python/Node/Flutter 검사와 오프라인 통합 검사, 기본 실기기 흐름, DB 보존을 확인하고 변경 커밋/남은 제한/팀원 결과 미수신 항목을 보고한다. 자동 확인을 중단한다.

팀원용 목록은 `docs/team-qa-checklist.md`, 기술 QA는 `docs/device-qa-plan.md`. 팀원 결과가 아직 없어도 독립적으로 할 수 있는 코드 리뷰·검사를 계속하며 팀원 검증 완료로 표시하지 않는다.

### 2026-10-20 진행 조정

USB 연결이 끊겨 최신 제품 실기기 재검증은 차단됐지만, 해당 QA 실행은 종료된 상태다. 비차단 작업으로 여섯 영역의 읽기 전용 리뷰를 완료했고 소스·설정 203개 및 제외 사유가 있는 생성 파일·바이너리 42개의 지문을 확인했다. 수정 전 245개 파일은 `local_artifacts/qa_orchestration/pre_full_fix_baseline`에 보존했다.

이제 기존 여섯 High 채팅에서 소유 파일을 나누어 오프라인 수정을 진행한다. data 담당이 DB 메타데이터·ID·근거 URL과 `data_pipeline.py`의 주소/좌표 검증을 함께 맡고, collection 담당은 수집 저널·CSV 저장·검색 응답·collector URL 접착부를 맡는다. engine은 추천/입력 해석, API는 Node, Flutter는 앱/플랫폼, integration은 검사 격리와 실행 문서를 맡는다. 공유 파일을 임의로 동시에 수정하지 않는다. 상세 담당과 새 턴은 state.json에 기록한다.

실행 중인 서버·설치 APK·휴대폰은 이 단계에서 교체하지 않는다. 코드 수정 완료 뒤 독립 통합 검사를 하고, USB 재연결 시 최신 코드로 APK를 다시 빌드하여 단일 QA 담당이 검증한다. 이전 APK 검사나 오프라인 회귀를 새 코드의 실기기 통과로 간주하지 않는다.

## 추천 품질 검증 설계

- 비교 축: 천안/아산, 자동차/대중교통, 음식/카페/자연/문화/실내, 스팟/코스, 일반/구체적/부정 문장, 수량·슬롯 경계. 각 축을 섞은 고정 입력을 기록한다.
- 논리 검증: 한 코스/스팟 목록의 동일 ID 중복, ID가 달라도 이름·주소·좌표가 같은 실제 장소 중복 의심, 슬롯·카테고리 일치, 유한 좌표/점수, 후보 부족에 따른 안내.
- 다른 코스 사이 장소 공유 및 동일 입력 재추천 결과 반복은 곧바로 오류가 아니다. 완전히 동일한 코스의 중복과 대안 간 겹침률을 따로 측정한다.
- 실제 정보 대조: 추천 결과에서 고정한 20~30개 표본을 지역·종류별로 선정하고 장소 ID·이름·주소·추천 조건·선정 이유·확인일을 남긴다. 최소 5개 동명/지점 사례를 확보할 수 있는지 확인하되 부족하면 실제 수를 보고한다. 공식 시설 정보·공개 지도 등 확인 가능한 출처로 대조한다. 읽기 전용 공개 정보 조회와 필요한 제한적 API 호출만 수행하며 대량 수집·DB 갱신은 하지 않는다.
- 신원 일치율, 활동/카테고리 적합률, 중복률, 후보/태그 커버리지, 코스 다양성, 주관적 취향 적합을 분리한다. 확인 불가·실패·0건을 분모에서 숨기지 않는다. 태그 0건인 현재 DB로 블로그 기반 취향 정확도를 검증했다고 말하지 않는다.
- 실제 교통시간·영업 여부·현장 분위기는 검증 근거가 있는 범위만 보고한다. 방문하지 않았거나 자료가 충돌하면 미확인이다.
- 팀원 표본과 자동/오프라인/실기기 표본을 섞어 하나의 정확도 숫자로 발표하지 않는다.
